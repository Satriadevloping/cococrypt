How it works

The password runs through PBKDF2-SHA256 in your browser. Each pair of peers also runs an ephemeral ECDH P-256 exchange. Both secrets feed HKDF to produce the AES-GCM-256 key for that pair. Messages are signed with a per-session ECDSA P-256 key.

Messages live in memory only. Refreshing or closing the tab erases them. Read the FAQ for what this does not protect against.

FAQ

How are messages encrypted?
Your password and the room ID go through PBKDF2-SHA256 (100,000 iterations by default). Every pair of peers also generates fresh ECDH P-256 keys for the session. HKDF-SHA256 combines the ECDH shared secret with the password-derived secret. The result is an AES-GCM-256 key used with a random 96-bit IV per message. Each message is signed with an ECDSA P-256 key generated for the session.
Why ECDSA and not the ECDH key for signatures?
ECDH keys cannot sign in Web Crypto. A separate ephemeral ECDSA key is generated alongside the ECDH key. Its public half is the key fingerprint you compare.
What does the server see?
The PeerJS signaling server sees random peer IDs, the fact that two of them connected, when, and the IP addresses that connected to it. It relays connection setup data (SDP and ICE candidates). It does not see passwords, keys or message content.
What is forward secrecy here?
Session keys come from ephemeral ECDH keys that exist only in memory and are discarded when you leave. Someone who records the encrypted traffic and later learns the password still lacks the ECDH private keys, so they cannot decrypt the recording.
What should I compare with the other person?
Open a peer's profile. Read the pair code aloud over a separate channel (phone, in person). If it differs on the two screens, someone is in the middle. Mark the peer as verified only after the codes match.
What this does not protect against
  • Peers connected directly can see each other's IP address. Use a VPN or a TURN relay if that matters.
  • A malicious peer who knows the password can read everything in the room and can save it.
  • Kick, ban, block, file download limits and self-destruct timers depend on the other clients cooperating. A modified client can ignore them.
  • Malware, browser extensions, screen recorders and cameras pointed at your screen.
  • A tampered copy of this page. Get the file from someone you trust and compare its hash.
  • Weak passwords. A short password can be guessed offline by anyone who captures a handshake.
  • Traffic analysis: timing and size of messages are visible to network observers.
What happens when everyone leaves?
There is no server copy. When the last browser tab closes, the messages are gone.
Does it work in Tor Browser?
Not by default. Tor Browser disables WebRTC. See the comment block at the top of the file for details.
Why do voice calls not use the AES layer?
Browser audio goes through WebRTC's media stack, which is encrypted with DTLS-SRTP between the two browsers. Adding a second layer needs APIs that differ between browsers, so it is not done here. The call is still encrypted; the key is negotiated by WebRTC, not by the room password.
Can recipients record calls or save files?
Yes. The app does not record calls, but nothing stops the other side from recording its speakers or saving a file.

What is collected

Nothing. There are no accounts, no cookies, no analytics, no tracking pixels, and no browser storage. Settings live in page memory and disappear when the tab closes.

Third parties

PeerJS 1.5.4 is loaded from cdn.jsdelivr.net with an integrity hash. The CDN operator can see that your browser requested the file, as with any web request. PeerJS connects to the PeerJS signaling server (0.peerjs.com unless you configure your own) to exchange connection setup data. That server sees random peer IDs, timing and IP addresses. It never receives passwords, keys or message content.

Google's public STUN server (stun.l.google.com) is used by default to discover your public address for WebRTC. It sees your IP address. You can replace it in Settings.

Other peers

People in a room with you receive what you send and, over direct connections, your IP address. The operator has no control over what they do with it.
